Benchmark and environment · 105 tasks · Web, Game, DevOps, Mobile

When computer-use agents meet visual software engineering.

CUA-SWE provides a benchmark and environment where coding agents need to repair the software by using it and visually inspecting it. Each task gives the agent an editable project and the running application. Deterministic, task-specific tests then judge the repaired software on a clean copy of the project.

Same tasks, same tests.
One difference: can the agent see and use the app?

Every model attempts each task under two conditions with identical instructions, budgets and verification. The gap between them isolates what visual feedback and interaction contribute to software repair.

Condition 1

Code-only

Coding / CLI

  • Read and edit the project source
  • Run build, test and development commands
  • Inspect command output and logs
  • No screenshots, no mouse or keyboard, no view of the running app
Condition 2

Hybrid

Computer use + Coding / CLI

  • Everything in Code-only, plus:
  • Screenshot observations of the running application
  • Click, drag and scroll in the interface
  • Type, press and hold keys
  • Resize the viewport, wait, and navigate

The agent decides when to inspect code, run commands, look at the screen and revise. Codex and Claude Code are evaluated as complete agent systems in the Hybrid condition only. Task success also requires following each condition's tool-use rules: a Hybrid run that never looked at a screenshot does not count, even if its patch passes.

    A plausible patch
    is not enough.

    Each task specifies the failure to fix, the behavior to implement, and the existing functionality that must keep working. A submission counts as a repair only when all three checks hold.

    1

    Task check

    Does the requested behavior work?

    Tests drive the rebuilt application through interaction sequences and assert on the rendered interface and runtime state, under several service responses, layouts, seeds or inputs.

    2

    Regression check

    Does designated existing behavior still work?

    The same tests cover the functionality the task says must be preserved, so a fix that breaks normal play, editing or navigation fails.

    3

    Permitted-change check

    Did the patch stay inside the allowed scope?

    Edits outside the files the task permits fail regardless of test results, so the repair has to happen in the implementation rather than around it.

    success = task ✓ ∧ regression ✓ ∧ permitted changes ✓Evaluated on a clean copy of the project. Success rates count only submissions that pass all three and follow the condition's tool-use rules.

    Every test is validated against three versions before release

    1. Buggy baselinemust fail
    2. Plausible but incomplete repairmust fail
    3. Reference repairmust pass

    An incomplete repair handles one scenario and leaves the rest broken, such as hardcoding a single interaction. In the support-scheduling task, one such repair displayed the first appointment correctly but reused that value for the second. The tests reject it, and accept the reference repair that passes both service-response checks while preserving the schedule details.

    Verification is independent of the agent's own checks

    The evaluator applies the submitted patch to a fresh copy of the project and runs the protected tests there. The agent never sees them. The evaluator can also inspect state the agent cannot, such as game-board contents, to decide whether a requirement is met. For Hybrid runs, a trajectory audit confirms that the agent followed the tool-use rules and actually viewed its screenshots.
